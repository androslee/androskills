# Reference evidence and comparison protocol

## Build a usable source set

Use the installed reference game and authorized local captures when available.
Otherwise browse official gameplay, developer demonstrations, release notes,
manuals and store media; supplement missing mechanics with dated hands-on guides,
complete playthroughs or maintained community documentation. Prefer direct sources
and cross-check consequential secondary claims. Record version/date conflicts.
Do not publish private project details in searches. No purchases, game installation
or large downloads are implied by a reference-comparison task.

For each source record an ID, title, direct URL/local path, publisher/uploader,
publication date, reference build/platform/settings if known, access date, media
type and inspected range. Separate publication date from demonstrated build date.
Keep concise observations, confidence and limitations. Existing local reference
images with unknown provenance may guide appearance; they do not establish build
availability or complete mechanics.

For video, view the clip or inspect actual consecutive frames with timestamps,
using available browser/video tools or an authorized accessible media file. Keep
representative context frames as well as detail frames. Compare locomotion across
several phases (idle/start/turn/move/stop/contact); one trailer frame cannot prove
animation response, hit feedback or game rules. State whether you viewed motion,
only frames, only a transcript, or only a page description. If playback/download
is unavailable, retain the source as a lead and the motion claim as unverified;
do not bypass access controls or imply footage was watched. Avoid repeated large
media downloads when an existing short clip answers the question.

## Record mechanics without filling gaps from imagination

Use compact linked tables where helpful:

| Area | Facts worth extracting when visible |
| --- | --- |
| Levels/biomes | Name if documented, landmarks, routes, scale/depth, visual layers, hazards |
| Fauna/enemies | Silhouette, anatomy, scale, habitat, idle/locomotion/attack/flee response, audio cues |
| Items/tools | Purpose, acquisition, controls, reach/feedback, inventory/pickup behavior |
| Build/tech | Unlock source, recipe, station, prerequisites, placement/removal constraints |
| State/combat | Meters, resource rates if measured, recovery, damage, death and co-op ownership |
| Progression/events | Objective gates, rewards, journey endpoint, authored vs random/repeatable events |

Attach evidence to individual facts, not just an entire paragraph. Tech trees
need explicit prerequisite edges, not only a list of equipment names. A creature
being large does not establish a boss encounter. An observed wreck does not prove
random spawning or treasure rewards. A story ship does not establish an escape
ending. Label user-requested original adaptations separately from reference facts.
One supported feature is enough to create a bounded task while other fields stay
unknown. Date/branch unsupported claims rather than silently rewriting history.

## Create comparable local observations

Save reference/context and local baseline/result together with a small manifest:
artifact version or source hash, seed, coordinates, camera yaw/pitch/FOV, time,
viewport/device scale, quality, lights, render hardware and staging changes. Use
human-readable filenames containing task/iteration IDs; retain milestone captures.
Do not use a low-resolution software-rendered shot to claim hardware performance
or a cinematic still to claim normal gameplay readability. Different viewpoints
can support qualitative comparison if explicitly labeled, not pixel-matched A/B.

Judge silhouette/scale first, then anatomy/geometry, surface response, lighting,
color/visibility, composition/density and temporal behavior. Prioritize the largest
visible deficits over detail that cannot be seen at gameplay distance. Test both
close inspection and normal navigation. For mechanics, record the input/action,
expected result and actual result, including a meaningful failure case when useful.

Keep the review falsifiable: cite the relevant image region or time range, state
what remains visibly or mechanically wrong, and define what would pass next time.
Model agreement is not proof. Distinguish independently executed review from
same-model reinspection, and human preferences from verified reference facts.
